# cc-rail-path

货运列车跨多个区间与车站的**完整运行径路预留**服务。一条径路申请按顺序经过若干区间并在中间站停靠，系统在单个数据库事务内对全部区间与车站做容量校验并一次性写入占用，任一节点冲突都整体回滚，绝不留下部分径路。

## 技术栈

- JDK 21、Spring Boot 4.1.1、Spring Data JPA、Hibernate 7
- H2 内嵌数据库（可通过数据源配置切换）
- 数据库事务、行级悲观锁、唯一约束与检查约束
- JUnit 5 + MockMvc + AssertJ 自动化测试

## 核心领域

| 概念 | 说明 |
| --- | --- |
| 区间 `RailSection` | 代码、运行方向（`UP`/`DOWN`）、**通过能力**（同一时刻允许在区间内的最大列车数）、**最小追踪间隔**（相邻列车进入区间的最小秒数，`0` 表示不限制） |
| 车站 `Station` | 代码、**可用到发线数量**（同一时刻容许停靠的最大列车数） |
| 径路 `PathReservation` | 一个外部运行号对应一条径路，状态为 `ACTIVE` / `CANCELLED`，按顺序持有多个占用段 |
| 占用段 `PathLeg` | 在 `[entryTime, exitTime)` 内占用一个区间或一座车站，带顺序号 `seq` |
| 事件 `PathEvent` | 只追加、不可变的生命周期事件：`APPROVED` / `REROUTED` / `CANCELLED` |

## 主要业务规则

### 1. 径路按时间顺序连续

申请 `legs` 按运行先后给出，每段包含区间代码、进入时间、离开时间以及离开该区间后停靠的车站：

- 时间窗一律**左闭右开** `[进入, 离开)`：列车在离开时刻即释放资源，后续列车可在同一时刻进入；
- 每段离开时间必须严格晚于进入时间；
- 两段之间**停靠**某站时，车站占用为 `[上一区间离开, 下一区间进入)`，停靠时长必须为正；
- 两段之间**不停靠**（直接通过）时，下一区间必须在上一区间离开的同一时刻进入，时间轴上不得留空档；
- 最后一个区间段不允许再填写停靠车站（终到停靠不在本申请范围内）。

### 2. 区间与车站容量

- **区间通过能力**：把候选占用与所有有效径路的占用放在同一时间轴上扫描，任一时刻（左闭右开）在区间内的列车数不得超过能力；
- **最小追踪间隔**：即使两车占用时间窗不重叠，进入同一区间的时刻之差也不得小于配置的秒数；
- **车站到发线**：任一时刻在站停靠的列车数不得超过到发线数量；
- 已取消径路不参与任何容量计算。

### 3. 批准是原子操作

校验与写入在**同一事务**内完成：先对申请涉及的全部资源行加悲观写锁，再在最新占用数据上判定，全部通过后才写入径路与全部占用段并记录 `APPROVED` 事件。任一区间或车站不满足条件即抛出冲突并回滚，数据库中不会出现部分径路。

### 4. 外部运行号幂等

- 以 `externalRunNo` 为全局幂等键（数据库唯一约束）；
- 申请内容按“区间代码 + 时间 + 停靠车站”的规范化序列计算 **SHA-256** 存库；
- 相同编号 + 相同内容重放：直接返回原结果，不重复占用、不重复事件；
- 相同编号 + 不同内容：返回 `409 CONFLICT`；
- 并发提交相同编号时，唯一约束兜底，后到事务回滚后在新事务中读取并返回原结果。

### 5. 并发安全

- 事务先按固定全局顺序（区间代码升序、再车站代码升序）对资源行加 `PESSIMISTIC_WRITE` 锁，避免交叉加锁死锁；
- 争抢同一资源的并发申请在锁上排队，后到者在前者提交后才能读到最新占用，因此只有符合容量/追踪间隔限制的组合会成功；
- 径路实体带 `@Version` 乐观锁；
- 数据库另有唯一约束（外部运行号、`(径路,序号)`）和检查约束（能力为正、到发线为正、`离开 > 进入`）作为纵深防御。

### 6. 整体改线

- 仅**尚未发车**（当前时间早于首段进入时间）的径路可以改线，已发车返回 `409`；
- 新径路必须先**完整取得**全部新占用（校验时排除自身旧占用），通过后才在同一事务内替换旧占用与内容哈希；
- 任一节点冲突则事务回滚，**原计划完全不变**，也不产生改线事件；
- 改线记录 `REROUTED` 事件，详情快照含改线前后完整占用。

### 7. 取消与查询

- 取消将径路置为 `CANCELLED`、立即释放全部容量，操作幂等，记录 `CANCELLED` 事件；
- 取消后占用明细仍可查询（状态为 `CANCELLED`），事件永久保留；
- 可查询单条径路的完整占用明细、单个运行号的事件流，以及全部事件。

## HTTP 接口

基础路径 `/api`。请求/响应均为 JSON，时间使用 ISO-8601（如 `2026-10-01T08:00:00Z`）。

### 资源管理

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/resources/sections` | 注册区间 |
| GET | `/resources/sections` | 列出区间 |
| POST | `/resources/stations` | 注册车站 |
| GET | `/resources/stations` | 列出车站 |

```json
POST /api/resources/sections
{"code":"S1","direction":"UP","capacity":2,"minHeadwaySeconds":300}

POST /api/resources/stations
{"code":"ST-A","trackCount":3}
```

### 径路

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/paths` | 提交申请（幂等），成功返回 201 与完整占用 |
| GET | `/paths/{externalRunNo}` | 查询径路完整占用明细 |
| POST | `/paths/{externalRunNo}/reroute` | 整体改线（未发车） |
| POST | `/paths/{externalRunNo}/cancel` | 取消（幂等） |
| GET | `/paths/{externalRunNo}/events` | 查询该径路事件 |
| GET | `/paths/events` | 查询全部事件 |

```json
POST /api/paths
{
  "externalRunNo": "TRAIN-1",
  "legs": [
    {"sectionCode":"S1","entryTime":"2026-10-01T08:00:00Z","exitTime":"2026-10-01T08:10:00Z","stopStationCode":"ST-A"},
    {"sectionCode":"S2","entryTime":"2026-10-01T08:20:00Z","exitTime":"2026-10-01T08:30:00Z","stopStationCode":null}
  ]
}
```

上例展开为 3 个顺序占用：区间 `S1` 08:00–08:10、车站 `ST-A` 08:10–08:20、区间 `S2` 08:20–08:30。

## 统一错误模型

所有错误返回相同信封，分为四类：

| 类别 `error` | HTTP | 典型场景 |
| --- | --- | --- |
| `VALIDATION` | 400 | 参数缺失/格式错误、时间不连续、停靠时长非正 |
| `RESOURCE_NOT_FOUND` | 404 | 引用的区间或车站不存在、径路不存在 |
| `CAPACITY_EXCEEDED` | 409 | 超过区间能力/到发线数、违反最小追踪间隔；带 `conflicts` 明细（资源、时间窗、冲突运行号） |
| `CONFLICT` | 409 | 同号内容不一致、已发车改线、资源重复注册、并发修改 |

```json
{
  "timestamp": "2026-09-27T00:00:00Z",
  "status": 409,
  "error": "CAPACITY_EXCEEDED",
  "code": "CAPACITY_CONFLICT",
  "message": "径路占用与既有计划冲突……",
  "conflicts": [
    {"resourceType":"SECTION","resourceCode":"S1","reason":"……",
     "windowStart":"…","windowEnd":"…","conflictingRunNos":["TRAIN-1"]}
  ]
}
```

## 常用命令

运行全部测试（含并发争抢容量、追踪间隔、改线回滚、幂等等场景）：

    ./mvnw clean test

启动服务：

    ./mvnw spring-boot:run

默认使用内存 H2（`jdbc:h2:mem:railpath`），重启后数据清空；可在 `src/main/resources/application.properties` 中切换数据源。
